# 研究结论：首次账号入口

## 决策 1：入口先按服务端会话分流

- **决定**：`/` 在读取当前身份后决定渲染账号入口或现有应用首页；无会话时不查询衣橱业务数据。
- **理由**：避免客户端先显示应用再跳转，也让未选择身份前不产生业务请求或匿名身份副作用。
- **备选**：新增 `/welcome` 再跳转。未采用，因为会改变固定首页和所有现有导航链接。

## 决策 2：彻底移除自动匿名初始化

- **决定**：`SessionBootstrap` 不再在任意业务路由自动调用匿名接口；匿名会话只由“体验使用”按钮触发。
- **理由**：Supabase `signInAnonymously()` 会真实创建 Auth 用户，必须对应用户明确意图。未登录深链接返回统一入口。
- **备选**：只在 `/` 跳过自动初始化。未采用，因为直接打开衣橱或推荐仍会悄悄创建体验身份。

## 决策 3：直接邮箱密码注册以有效会话为完成信号

- **决定**：无会话用户使用 `signUp({ email, password })`；只有返回用户和有效会话才进入 App。若用户存在但无会话，提示直接登录；若新身份存在但无会话，提示检查“确认邮箱”配置。
- **理由**：Supabase 当前文档说明 `signUp` 创建邮箱密码账号；关闭 Confirm email 时应立即建立会话。把 `session` 作为门禁可避免误把“等待邮件”当成成功。
- **备选**：客户端本地保存密码或自建用户表。未采用，因为会降低密码安全并绕过现有 Auth/RLS 身份体系。

## 决策 4：兼容体验账号原地升级

- **决定**：同一个注册 Action 同时支持无会话直接注册和现有匿名账号原地升级。匿名升级继续先绑定邮箱、再设置密码，保持原用户 ID。
- **理由**：现有衣物、偏好、推荐和收藏均以 Auth 用户 ID 归属，原地升级不会搬迁数据。
- **备选**：为匿名升级另建新账号并复制数据。未采用，因为增加数据迁移、冲突和跨用户授权风险。

## 决策 5：视觉延续产品而非制作宣传页

- **决定**：使用现有冷白银灰、近黑主按钮、系统蓝焦点、24px 软圆角和克制的 Liquid Glass；以登录/注册分段选择为唯一视觉记忆点，体验入口保持次级。
- **理由**：入口的单一工作是选身份并进入衣橱，信息层级比装饰重要；同时延续已有苹果式移动端质感。
- **备选**：大幅渐变 Hero、插画或多张悬浮卡片。未采用，因为会增加 AI 模板感并挤压移动端表单空间。

## 当前文档核对

- Supabase JavaScript `signUp` 支持邮箱和密码直接注册；`signInWithPassword` 用于现有邮箱密码登录；`signInAnonymously` 会创建新的匿名用户。
- Supabase 更新索引中没有影响托管项目邮箱密码注册的近期破坏性变更；Node.js 20 支持已在 2026-06-30 停止，项目部署环境继续使用当前受支持运行时。
- Next.js 16 项目内文档建议使用 Server Action 处理认证提交、服务端校验字段，并以 `useActionState` 展示等待和字段错误。
