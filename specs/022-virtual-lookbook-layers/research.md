# 技术研究：虚拟模特与分层穿搭

## 决策 1：单套按需生成而非三套自动生成

- **决定**：用户在推荐卡上点击后生成该套效果图；生成成功后缓存。
- **理由**：普通推荐保持快速，未查看的套装不产生图像费用，失败也不阻塞三套推荐。
- **备选**：每次推荐自动生成 3 张；因成本、延迟和限流风险较高而不采用。

## 决策 2：使用 Image API 的单次生成

- **决定**：服务端使用 `gpt-image-2` 的单次 Image API，读取 base64 图片结果。
- **理由**：OpenAI Docs 明确建议单提示生成单图使用 Image API；本阶段不需要多轮图像编辑。
- **备选**：Responses API 图像工具；适合多轮编辑，但会增加主模型调用成本和状态复杂度。

## 决策 3：保留实拍，效果图只作参考

- **决定**：动态图放在推荐卡主视觉区，真实衣物拼图与角色清单始终保留。
- **理由**：纯文本生成图可能存在颜色、细节和版型偏差，实拍是最终可信来源。
- **备选**：只展示生成图；会误导用户并削弱换件、收藏和衣物核对能力。

## 决策 4：复用私有衣物 bucket

- **决定**：路径使用 `<user-id>/lookbooks/<recommendation-id>/<slot>.png`，RLS 继续按第一段账号所有权约束，读取使用短期签名 URL。
- **理由**：Supabase 私有 bucket 的上传、读取和签名能力已存在，无需新表或公开资产域。
- **备选**：公开静态 URL 或新增 bucket；前者泄露用户衣橱推断信息，后者增加配置与迁移成本。

## 决策 5：角色由分类派生

- **决定**：推荐仍以 `itemIds` 为单一事实源，读取时稳定派生角色；两件上装时较轻的一件为内搭。
- **理由**：兼容所有历史推荐和换件链路，避免 `itemIds` 与角色映射双写不一致。
- **备选**：持久化独立角色数组；会增加 AI 输出和替换后的同步风险。
