# Feature Specification: 设备定位天气城市

**Feature Branch**: `020-device-location-weather`

**Created**: 2026-08-31

**Status**: Complete

**Input**: User description: "手机端增加自动定位，让天气可以按用户当前位置变化；实现应简单、可控，并继续保证天气是真实数据。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 主动使用当前位置 (Priority: P1)

用户来到新的城市后，可以在推荐页主动点击“使用当前位置”，授权手机定位并把当前城市用于今天或明天的真实天气搭配。

**Why this priority**: 这是解决旅行或移动后天气仍停留在旧城市的最直接路径，同时保留用户对定位权限和天气城市的控制。

**Independent Test**: 账号常用城市为武汉，测试设备定位到杭州；用户点击并授权后选择“本次使用”，页面显示杭州，武汉常用城市不变，重新生成的推荐使用杭州真实天气。

**Acceptance Scenarios**:

1. **Given** 用户已登录并打开推荐页，**When** 用户点击“本次使用当前位置”并授权定位，**Then** 系统确认所在中国城市并仅在当前浏览器会话使用该城市。
2. **Given** 用户没有点击定位操作，**When** 页面打开或刷新，**Then** 系统不得请求设备定位权限或改变天气城市。
3. **Given** 定位成功但城市确认服务或真实天气不可用，**When** 操作结束，**Then** 页面显示可理解的错误并保留原城市，不使用默认或模拟天气。

---

### User Story 2 - 保存为常用城市 (Priority: P1)

用户确认当前位置是长期居住地后，可以把定位得到的城市保存为账号常用城市，使刷新、重新登录和其他设备继续使用该城市。

**Why this priority**: 临时旅行和长期迁移含义不同，必须给用户明确的持久化选择，避免一次定位意外覆盖账号偏好。

**Independent Test**: 用户定位到杭州后选择“设为常用城市”，确认刷新和重新登录后仍显示杭州；另一个账号不受影响。

**Acceptance Scenarios**:

1. **Given** 设备定位到受支持城市，**When** 用户点击“设为常用城市”，**Then** 规范城市写入当前账号并清除旧的临时城市。
2. **Given** 常用城市保存成功，**When** 用户刷新、退出并重新登录，**Then** 页面继续使用新城市的真实天气。
3. **Given** 两个隔离账号使用同一设备，**When** 其中一个账号保存定位城市，**Then** 另一个账号的常用城市和推荐不得改变。

---

### User Story 3 - 拒绝或无法定位时继续使用 (Priority: P2)

用户拒绝定位、设备不支持定位或定位超时后，仍可继续使用现有城市和手动选择城市，不会被卡住。

**Why this priority**: 设备定位是便捷入口，不应成为天气或推荐的必经条件。

**Independent Test**: 模拟权限拒绝、定位超时和不支持三种情况，页面分别给出简短说明，原城市保持不变，手动城市输入仍可提交。

**Acceptance Scenarios**:

1. **Given** 用户拒绝定位权限，**When** 定位请求返回，**Then** 页面说明可在浏览器设置中开启，并保留手动选城入口。
2. **Given** 定位超时或设备暂时不可用，**When** 请求失败，**Then** 页面允许重试且不修改任何城市状态。
3. **Given** 浏览器不支持设备定位，**When** 用户点击定位，**Then** 页面提示改用手动选城，不出现崩溃或空白状态。

### Edge Cases

- 坐标为空、非数字或超出经纬度范围时，服务器拒绝处理并保持原城市。
- 定位结果在中国大陆以外时，当前版本提示使用手动城市，不错误映射为国内城市。
- 反向城市确认返回区县、县级市或直辖市时，必须整理为既有天气系统可识别的中国城市名。
- 定位按钮被连续点击时，操作保持单次进行状态，不并发提交多个城市切换。
- 当前城市改变后，今天和明天的旧城市推荐全部失效，避免继续展示旧天气。
- 精确坐标只用于本次城市确认，不写入数据库、Cookie、日志或浏览器长期存储。
- 公共城市确认服务限流或不可用时，不循环重试、不自动切换其他供应商、不阻塞手动选城。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 只在用户明确点击定位按钮后请求设备定位权限，不得在页面加载、刷新或后台自动请求。
- **FR-002**: 用户 MUST 能分别选择“本次使用当前位置”和“设为常用城市”。
- **FR-003**: “本次使用当前位置” MUST 只改变当前账号、当前浏览器会话的有效天气城市，不修改账号常用城市。
- **FR-004**: “设为常用城市” MUST 只更新当前登录账号的常用城市，并清除旧的临时城市。
- **FR-005**: 浏览器 MUST 校验设备坐标范围并只接受基于当前坐标返回的中国城市；服务器 MUST 从当前有效会话派生用户身份，把客户端城市名视为不可信输入并再次规范化，不接收客户端用户 ID、行政区、时区或设备坐标。
- **FR-006**: 系统 MUST 在设备端把当前坐标确认到受支持的中国城市，再把城市名交给既有城市规范化流程取得天气所需的城市、行政区、城市中心坐标和时区。
- **FR-007**: 系统 MUST NOT 把设备精确坐标写入数据库、Cookie、日志、分析事件或浏览器长期存储。
- **FR-008**: 任一有效城市切换 MUST 删除当前用户的旧推荐，使后续结果重新读取新城市的真实天气。
- **FR-009**: 定位、城市确认或保存失败时 MUST 保持原城市，不得回退到武汉、北京、IP 城市或任何模拟位置。
- **FR-010**: 权限拒绝、不支持、超时和设备不可用 MUST 显示各自可行动的用户提示，并保持手动选城入口可用。
- **FR-011**: 页面 MUST 说明定位只在点击后触发、只用于城市级天气，精确坐标不会保存。
- **FR-012**: 页面 MUST 标明城市名称数据来源，并提供符合来源要求的署名入口。
- **FR-013**: 定位请求 MUST 以城市级需求为准，不要求高精度，并设置有限等待时间与短期位置缓存。
- **FR-014**: 本阶段 MUST NOT 新增数据库表、迁移、第三方依赖、环境变量、持续定位、位置历史、地图或海外天气城市支持。
- **FR-015**: 现有手动城市、确认式 IP 建议、临时城市恢复和真实今天/明天天气功能 MUST 继续可用。

### Key Entities

- **设备坐标输入**: 用户点击后由浏览器短暂提供的纬度和经度，只用于单次城市确认，不持久化。
- **设备定位城市**: 设备端根据当前坐标确认、再由服务器规范化的中国城市级位置；应用服务器不接收设备精确坐标。
- **本次天气城市**: 已有账号绑定会话状态，设备定位选择“本次使用”时复用。
- **账号常用城市**: 已有账号偏好中的规范城市五元组，设备定位选择“设为常用城市”时复用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 未点击定位按钮时，测试页面加载和刷新产生的设备定位权限请求数为 0。
- **SC-002**: 在支持定位且城市确认服务正常时，用户可在 2 次交互内完成当前位置切换，目标 10 秒内看到结果。
- **SC-003**: 定位成功后的天气与推荐使用确认城市真实数据的比例为 100%，默认城市或模拟天气发生率为 0%。
- **SC-004**: 固定样本中的非法坐标、非中国位置、权限拒绝、超时和服务不可用均保持原城市，错误覆盖率为 100%。
- **SC-005**: 两个隔离账号互相修改常用城市或继承本次城市的成功率为 0%。
- **SC-006**: 精确设备坐标出现在数据库、Cookie、日志和长期浏览器存储中的次数为 0。
- **SC-007**: 390px 宽度下，定位说明、双操作按钮、结果提示和手动选城无水平溢出或按钮重叠。

## Assumptions

- 用户已同意推荐方案：定位必须由本人点击触发，并保留“本次使用”和“设为常用城市”两种结果。
- 当前产品范围继续只支持中国大陆城市；海外位置不自动映射，用户仍可使用现有手动能力支持范围。
- 城市级天气不需要高精度定位，优先降低权限敏感度、耗电和等待时间。
- 设备坐标只在一次浏览器到服务器请求和一次城市确认请求中短暂存在，不建立位置历史。
- 城市确认采用可替换的服务端适配边界；公共服务不可用时保持手动选择，不影响核心推荐功能。
