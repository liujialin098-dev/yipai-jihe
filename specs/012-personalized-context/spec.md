# Feature Specification: 账号城市与衣着偏好

**Feature Branch**: `master`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "天气按照登录人的地址来；增加性别选择，男生衣橱不再出现裙子等不适合的演示衣物。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 保存常用城市并使用当地天气 (Priority: P1)

登录用户可以在个人偏好中填写常用城市。系统确认城市后，将它保存到当前账号，并在生成每日推荐时使用该城市的实时天气，不再默认使用北京。

**Why this priority**: 错误城市会直接导致温度、降雨和推荐衣物不可信，是每日推荐核心结果的前置条件。

**Independent Test**: 将账号城市设为武汉，生成实时天气推荐，页面显示武汉及其当前天气；退出并重新登录后仍使用武汉。

**Acceptance Scenarios**:

1. **Given** 当前账号尚未设置城市，**When** 用户打开偏好页，**Then** 页面明确提示先保存常用城市，且推荐不会把北京伪装成用户所在地。
2. **Given** 用户填写“武汉”，**When** 城市被确认并保存，**Then** 当前账号记录武汉及对应位置，并清除可能使用旧城市的当日方案。
3. **Given** 当前账号已保存武汉，**When** 用户使用实时天气生成推荐，**Then** 天气卡显示武汉、实时来源、天气概况和体感温度。
4. **Given** 城市无法识别或天气服务失败，**When** 用户保存或生成推荐，**Then** 页面保留原设置并给出可重试的说明，不展示错误城市。

---

### User Story 2 - 按衣着偏好整理衣橱与推荐 (Priority: P1)

用户可以选择“男装”“女装”或“不限”。男装用户不会在日常衣橱和新推荐中看到明确标记为女装的单品，女装用户同理，不限用户保留全部单品。

**Why this priority**: 不适合用户的裙装等单品会降低衣橱可信度，并可能进入推荐结果。

**Independent Test**: 加载演示衣橱后选择男装，衣橱列表和新生成的三套推荐中均不包含连衣裙；改回不限后这些单品重新可见，数据库记录没有被删除。

**Acceptance Scenarios**:

1. **Given** 演示衣橱已包含裙装，**When** 用户保存男装偏好，**Then** 日常衣橱、首页预览和新推荐均排除明确女装单品。
2. **Given** 用户选择女装，**When** 浏览衣橱或生成推荐，**Then** 明确男装单品被排除，中性单品继续保留。
3. **Given** 用户选择不限，**When** 浏览衣橱，**Then** 所有本人可见衣物均正常显示。
4. **Given** 用户切换衣着偏好，**When** 保存完成，**Then** 原衣物不被删除，切回原选项可恢复显示。

---

### User Story 3 - 看懂当前个性化状态 (Priority: P2)

用户在设置页能够一眼看到当前城市和衣着偏好，并能进入同一个偏好页面修改。

**Why this priority**: 可见的账号状态能解释为什么天气和衣橱发生变化，减少“系统猜错了”的困惑。

**Independent Test**: 保存武汉和男装后返回设置页，摘要显示“武汉”“男装”，刷新页面后保持不变。

**Acceptance Scenarios**:

1. **Given** 城市和衣着偏好已保存，**When** 用户打开设置页，**Then** 默认偏好摘要显示对应值。
2. **Given** 城市尚未保存，**When** 用户打开设置页，**Then** 城市摘要显示“待设置”，并提供清晰编辑入口。

### Edge Cases

- 同名城市存在多个候选时，只接受中国境内最相关的城市级结果，并在保存结果中显示省级行政区辅助确认。
- 城市名为空、只有一个字符、过长或无法匹配时，不覆盖账号原有城市。
- 城市解析成功但实时天气暂时不可用时，允许使用明确标识的模拟天气，模拟天气仍显示账号保存的城市。
- 历史当日推荐使用旧城市或已被当前衣着偏好排除的单品时，不继续展示为当前有效方案。
- 未设置衣着偏好的既有账号默认“不限”，避免静默隐藏用户已有衣物。
- 用户自己上传但尚未识别出衣着归属的旧单品按“中性”处理，不做破坏性删除。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许当前账号保存一个常用城市，并在再次登录后恢复该设置。
- **FR-002**: 系统 MUST 将用户输入的中国城市解析为规范城市名、位置坐标和时区；解析失败不得覆盖原设置。
- **FR-003**: 系统 MUST 使用当前账号保存的位置获取实时天气，不得在未设置时静默回退到北京。
- **FR-004**: 系统 MUST 在天气服务失败时保留城市上下文，并将降级来源明确标为模拟天气。
- **FR-005**: 系统 MUST 允许用户选择男装、女装或不限，并按账号保存。
- **FR-006**: 系统 MUST 为衣物记录衣着归属：男装、女装或中性；既有未分类单品默认中性。
- **FR-007**: 系统 MUST 在衣橱列表、首页预览和推荐候选中排除与当前衣着偏好明确冲突的单品；中性单品始终可见。
- **FR-008**: 系统 MUST 保留被偏好过滤的原衣物记录，不得因切换偏好删除或归档单品。
- **FR-009**: 系统 MUST 在城市或衣着偏好变化后使旧的当日推荐失效，避免继续显示旧上下文结果。
- **FR-010**: 系统 MUST 在设置摘要中展示当前城市和衣着偏好，并提供统一编辑入口。
- **FR-011**: 系统 MUST 保持所有偏好和衣物数据仅对当前账号可读写，沿用既有账号所有权隔离。
- **FR-012**: 系统 MUST 为城市解析、天气失败、保存失败和未设置状态提供通俗且可操作的反馈。

### Key Entities

- **账号个性化偏好**: 当前账号的常用城市、规范位置、时区和衣着偏好；与账号一一对应。
- **衣物衣着归属**: 单件衣物适合男装、女装或中性穿着，用于可逆筛选和推荐候选约束。
- **天气快照**: 某账号城市在推荐生成时的天气、体感温度、来源和观测时间，随当日方案保存。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可在 30 秒内完成城市和衣着偏好设置，并立即看到保存结果。
- **SC-002**: 将城市设为武汉后，100% 的新实时天气推荐显示武汉，不再显示北京。
- **SC-003**: 男装账号的演示衣橱和新推荐中，明确女装单品出现率为 0%；女装账号对明确男装单品同样为 0%。
- **SC-004**: 切换至不限后，100% 被偏好隐藏的本人衣物可重新显示，且无记录丢失。
- **SC-005**: 两个测试账号不能读取或修改对方的城市、衣着偏好或衣物归属。
- **SC-006**: 城市解析或天气服务失败时，用户看到明确错误或模拟来源，错误城市展示率为 0%。

## Assumptions

- 登录身份本身不可靠地包含居住地址，因此本阶段以账号保存的常用城市作为“登录人的地址”。
- 本阶段只保存城市级位置和天气所需坐标，不保存街道、门牌或持续定位轨迹。
- 城市输入先支持中国城市名称；用户可随时修改，未来再扩展设备定位和多城市。
- 衣着偏好描述推荐和筛选方向，不等同于法律或生理性别；“不限”用于不希望系统过滤的用户。
- 演示裙装标记为女装，其余现有演示衣物优先标为中性，确保男装选择仍可组成三套完整搭配。
- 本阶段不根据姓名、邮箱、IP 或设备信息猜测城市或衣着偏好。
