# Feature Specification: 每日 3 套 AI 推荐

**Feature Branch**: `main`

**Created**: 2026-08-24

**Status**: Ready for planning

**Input**: 用户希望继续 SDD-005，在已有真实衣橱基础上生成每日 3 套可解释穿搭；普通实现选择由 AI Agent 采用推荐方案，账号登录、付费、密钥或产品方向选择才暂停。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 得到今天可直接照着穿的三套方案 (Priority: P1)

用户打开推荐页，选择今天的场合后生成推荐，看到恰好 3 套由自己衣橱真实单品组成的完整穿搭。每套展示衣物原图、搭配名称、理由与风格标签。

**Why this priority**: 这是“衣拍即合”从衣物管理走向穿搭决策的核心价值，也是本阶段可独立演示的最小闭环。

**Independent Test**: 当前用户加载完整演示衣橱，选择“通勤”并生成；页面出现 3 套方案，每个引用的单品都能在该用户衣橱中找到，三套之间没有重复单品。

**Acceptance Scenarios**:

1. **Given** 当前用户有足够的活跃衣物，**When** 选择场合并生成，**Then** 在 15 秒内得到恰好 3 套有名称、理由、标签和真实单品图片的方案。
2. **Given** 当天已有一个推荐批次，**When** 用户再次进入推荐页，**Then** 直接看到该批次，不会自动新增第二个批次。
3. **Given** 当天已有推荐，**When** 用户手动刷新，**Then** 新结果覆盖当天批次，数据库仍只保留一个当天批次。

---

### User Story 2 - 根据天气和场合重新生成 (Priority: P2)

用户可以在通勤、休闲、约会和正式场合之间切换，并可使用实时天气或测试天气重新生成，理解系统为何选择这些衣物。

**Why this priority**: 天气与场合让推荐从随机灵感图变成与“今天”有关的实际决策。

**Independent Test**: 分别选择通勤与约会，再切换冷天、热天和雨天测试天气；生成结果的理由和衣物季节适配随输入变化，页面明确显示使用的天气来源。

**Acceptance Scenarios**:

1. **Given** 天气服务可用，**When** 用户使用实时天气生成，**Then** 页面显示北京的当前温度、体感温度、天气概况和实时来源。
2. **Given** 用户选择测试天气，**When** 重新生成，**Then** 结果使用所选测试温度与天气，且明确标为模拟数据。
3. **Given** 用户切换场合，**When** 重新生成，**Then** 三套方案都与新场合相符，并覆盖原批次。

---

### User Story 3 - 外部服务失败时仍得到建议 (Priority: P3)

当天气或 AI 服务未配置、超时、限流或返回无效结果时，用户仍能得到由规则模板生成的 3 套方案，并能看懂当前使用了降级结果。

**Why this priority**: 核心页面不能因为外部服务短暂不可用而完全失去价值。

**Independent Test**: 分别模拟天气失败与 AI 失败；页面仍在 15 秒内显示 3 套仅引用当前用户衣橱的方案，并标明模拟天气或规则推荐。

**Acceptance Scenarios**:

1. **Given** 天气服务失败，**When** 用户生成，**Then** 系统使用温和天气默认值并明确标注“模拟天气”。
2. **Given** AI 未配置、超时、限流或结果不合法，**When** 用户生成，**Then** 系统自动使用规则模板并明确标注“规则推荐”。
3. **Given** 当前衣橱不足以组成 3 套互不重复的合理方案，**When** 用户生成，**Then** 页面提示先补充缺少类别，不保存残缺批次。

### Edge Cases

- 当前用户没有衣物、只有归档衣物或缺少组成完整穿搭所需的上装/下装/连衣裙与鞋时，不调用 AI，直接给出可执行的补充提示。
- 衣橱恰好只能组成 3 套时，允许确定性复用生成逻辑，但同一批次内任何单品不得跨套重复。
- AI 返回不存在、已归档或属于其他用户的单品 ID 时，整份 AI 结果视为无效并使用规则推荐，不部分采纳。
- AI 返回重复 ID、类别结构不完整、季节不匹配或场合不匹配时，整份结果视为无效并使用规则推荐。
- 天气请求超过 4 秒、响应字段缺失或数值异常时，使用模拟天气，不阻塞推荐。
- 用户快速连续提交时，服务端按当前用户和当天日期覆盖同一批次，最终只保留一条记录。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持通勤、休闲、约会和正式四种推荐场合。
- **FR-002**: 系统 MUST 默认读取可配置固定城市的实时天气；本阶段默认城市为北京，天气服务无需用户提供密钥。
- **FR-003**: 系统 MUST 在天气不可用时使用明确标识的模拟天气，并允许用户主动选择冷天、热天和雨天测试预设。
- **FR-004**: 系统 MUST 只向服务端推荐能力提供当前用户活跃衣物的必要摘要、天气、场合和现有偏好，不发送衣物原图。
- **FR-005**: 真实 AI 成功时 MUST 返回恰好 3 套结构化方案；每套包含 2-5 个真实单品 ID、简洁名称、搭配理由和 1-3 个风格标签。
- **FR-006**: 系统 MUST 验证所有推荐单品属于当前用户且处于活跃状态，并验证类别结构、季节、体感温度、场合及同批次跨套不重复。
- **FR-007**: 每套方案 MUST 包含一件连衣裙，或同时包含上装与下装；除明确测试降级外，每套还 MUST 包含鞋，可按天气增加外套并可选配饰。
- **FR-008**: 推荐页 MUST 使用现有原图缩略图展示搭配版位，不依赖透明底图或自动抠图。
- **FR-009**: 同一用户同一自然日 MUST 只保留一个推荐批次；手动刷新、切换场合或测试天气都覆盖该批次。
- **FR-010**: AI 未配置、超时、限流、服务异常或输出无效时，系统 MUST 自动生成恰好 3 套可解释的规则方案。
- **FR-011**: 推荐生成 MUST 在 15 秒内结束并展示生成中、成功、输入不足和失败状态；不能静默显示过期或虚构结果。
- **FR-012**: 所有推荐记录 MUST 按当前用户隔离；其他匿名或邮箱会话不得读取、修改或覆盖。
- **FR-013**: 系统 MUST 保存生成日期、场合、天气快照、来源、模型、耗时和 3 套结构化方案，用于同日读取与后续反馈阶段扩展。
- **FR-014**: 系统 MUST 继续支持匿名体验；SDD-002 的密码设置与重新登录验收不作为本阶段依赖。

### Key Entities

- **每日推荐批次**: 当前用户某一天唯一的一组推荐，包含场合、天气快照、生成来源、模型、耗时和 3 套方案。
- **推荐方案**: 批次中的一套完整穿搭，包含顺序、名称、理由、风格标签和当前用户衣物 ID 列表。
- **天气快照**: 生成时使用的城市、温度、体感温度、天气代码、概况、来源和观测时间，生成后不随实时天气变化。
- **衣物摘要**: 当前用户活跃衣物中用于推荐判断的 ID、名称、类别、颜色、材质、风格、季节和场合，不包含图片二进制数据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 具备完整演示衣橱的用户从提交到看到 3 套推荐不超过 15 秒。
- **SC-002**: 每次成功结果都恰好包含 3 套方案，引用单品的当前用户归属正确率为 100%，同批次重复单品数为 0。
- **SC-003**: 通勤、休闲、约会和正式四种场合均可独立完成生成并展示与所选场合一致的理由。
- **SC-004**: 在天气服务和 AI 服务分别失效的测试中，用户仍能获得 3 套可解释方案，核心完成率为 100%。
- **SC-005**: 同一用户同一天连续生成 3 次后，持久化批次数仍为 1，最后一次输入与展示一致。
- **SC-006**: 两组独立会话互相读取、修改或覆盖推荐的成功次数为 0。
- **SC-007**: 390px 宽移动页面无水平溢出，生成中布局与最终三套卡片布局稳定，主要操作可键盘聚焦并支持减少动态偏好。

## Assumptions

- 默认城市为北京，环境变量可覆盖城市名、纬度、经度和时区；本阶段不做定位授权和多城市选择。
- 天气服务采用无需密钥的公开实时天气接口；模拟天气既用于失败降级，也用于验收温度与雨天分支。
- 推荐模型复用项目已配置的 OpenAI 服务端密钥和默认轻量模型；模型名称可由服务端环境变量覆盖。
- 用户偏好只读取现有偏好表中的风格与场合数组；行为反馈权重在 SDD-006 实现。
- P0 不做自动抠图、虚拟试穿、穿搭日记、收藏和换一件；这些能力不进入本阶段。
- 密码设置与重新登录留到后续集中调试，不阻塞匿名用户完成每日推荐闭环。
