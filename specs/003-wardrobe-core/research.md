# Phase 0 研究：我的衣橱与演示数据

## 决策 1：服务端读取与 Server Action 变更

- **决定**：列表和详情使用 Server Component；加载、编辑、归档、恢复和删除使用独立 Server Action。
- **理由**：符合项目默认服务端边界，减少浏览器直接编排数据的状态复杂度；Next.js 16 会在 Action 中携带刷新后的服务端 UI，适合本阶段的表单变更。
- **安全要求**：每个 Action 视为公开入口，必须自行读取当前会话、校验输入并以当前用户约束目标记录。
- **未采用**：单独建设 REST API 或全客户端数据层；当前没有第三方调用方，额外接口只会增加重复鉴权和状态同步。

## 决策 2：URL 作为搜索筛选状态

- **决定**：类别、关键词、颜色、季节、场合和状态使用 URL 查询参数，由服务端组合查询。
- **理由**：刷新后状态不丢失，可复制结果链接，也无需引入客户端缓存或表单状态库。
- **未采用**：加载全部数据后浏览器内筛选；虽然 24 件演示数据可行，但无法自然延伸到用户后续增长的数据量。

## 决策 3：私有图片使用短期签名 URL

- **决定**：保留 `wardrobe-images` 私有 bucket，通过服务端批量创建短期签名 URL 展示列表和详情图片。
- **理由**：Supabase 私有 bucket 的对象下载受 `storage.objects` RLS 约束，签名 URL 可以在有限时间内供浏览器展示，而无需公开 bucket 或暴露服务端密钥。
- **未采用**：公开 bucket、永久公开 URL或 Service Role 代理下载；它们会削弱现有用户隔离边界或扩大服务端复杂度。

## 决策 4：固定目录 + 代码生成合成图

- **决定**：维护 24 个稳定演示模板，由服务端生成 SVG 衣物插画并写入每个用户的私有目录。
- **理由**：不使用真实个人照片，不增加二进制素材和授权风险；稳定 `demo_key` 便于幂等补齐，图片仍完整经过 Storage 隔离路径验收。
- **未采用**：远程图片链接、共享公共演示图、仓库内复制 24 张位图；远程资源不稳定，共享资源无法证明用户图片隔离，大量位图不利于维护。

## 决策 5：普通唯一约束保障幂等

- **决定**：`demo_key` 允许为空，并为 `(user_id, demo_key)` 建立普通唯一约束；同一用户的非空演示标识只能出现一次。
- **理由**：PostgreSQL 唯一约束允许多个空值，既支持未来手动衣物，又能被 Supabase upsert 的冲突目标直接引用。
- **未采用**：仅在应用层先查后写或使用部分唯一索引；前者存在并发重复，后者不便作为常规 upsert 冲突目标。

## 决策 6：显式 GRANT 与 RLS 双层控制

- **决定**：仅向 `authenticated` 授予衣物表 `SELECT/INSERT/UPDATE/DELETE`，撤销 `anon` 权限，并为四类操作设置 `auth.uid() = user_id` 的 RLS 策略。
- **理由**：Supabase 2026 年 Data API 行为要求公开 schema 表使用显式授权；GRANT 决定角色能否尝试操作，RLS 决定角色能操作哪一行，两者不能互相替代。
- **未采用**：依赖默认表权限或只配置 RLS；行为不够可复现，也不符合当前项目的最小授权基线。

## 决策 7：不新增测试框架

- **决定**：沿用 `npm run check`、`npm run build`，增加一个双匿名会话脚本，再用浏览器完成 390px 核心流程验收。
- **理由**：章程未要求完整自动化测试框架，本阶段用可重复的安全脚本和端到端手工验收即可覆盖主要风险。
- **未采用**：引入 Playwright/Vitest；会扩大单阶段依赖和配置范围。
