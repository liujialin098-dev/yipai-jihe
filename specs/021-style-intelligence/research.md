# 研究与决策

## 决策 1：品牌只在有视觉证据时返回

- **决定**：严格 Schema 返回 `brand` 与 `brand_confidence`；无清晰文字或标志时 `brand` 为空、置信度为 `unknown`。
- **理由**：外观相似不能证明品牌，错误品牌比空值更误导。
- **替代方案**：按款式猜品牌；因不可验证和潜在侵权风险拒绝。

## 决策 2：扩展为 14 个稳定主风格

- **决定**：在旧 6 类上增加 Clean Fit、街头、City Boy、Gorpcore、学院、工装、老钱、Y2K。
- **理由**：覆盖用户要求的新鲜潮流方向，同时保留单值主风格，避免本轮改造全部查询和评分模型。
- **替代方案**：衣物多风格数组；价值存在，但会显著扩大迁移、筛选、评分和推荐复杂度。

## 决策 3：风格选择是软目标，场景仍是硬边界

- **决定**：为四个场景定义兼容风格；自动模式分配最多 3 个不同方向，指定模式复用一个方向。若库存不足，回退兼容方向。
- **理由**：用户已明确要求休闲、约会、正式和通勤不要混穿；风格不能覆盖这一约束。
- **替代方案**：任何场景都可选任何风格；会重新引入场景雷同和不一致。

## 决策 4：趋势灵感采用可追溯快照

- **决定**：首批使用 2026 秋季 Vogue 与 GQ 编辑内容，保存摘要、发布日期、来源 URL 和有效期；页面不复制来源图片。
- **理由**：可以证明“新”，无需运行时抓取、额外密钥或不可控网络请求。
- **替代方案**：模型凭记忆生成、页面实时抓取、定时内容后台；分别存在时效不实、稳定性/版权和范围过大的问题。

## 文档与框架结论

- Supabase 官方模式继续使用服务端当前会话客户端，查询自动携带用户令牌并由 RLS 限制；Server Action 仍需显式验证身份。
- Next.js 16.3.1 项目内文档要求每个 Server Action 自行验证认证与授权，输入只能作为变更意图，所有权必须从会话与数据库重新派生。
- 本轮不引入新依赖；当前 Supabase 变更索引未发现影响普通 RLS 行更新或 PostgREST 数组字段的破坏性变更。
