# Phase 0 研究：应用框架与匿名数据底座

## 决策 1：匿名会话通过 Route Handler 自动启动

- **决定**：浏览器端的最小会话启动组件调用 `POST /api/session/anonymous`；Route Handler 使用现有 Supabase SSR server client 检查会话，没有会话时执行匿名登录，并在同一请求中初始化资料和默认偏好。
- **理由**：Next.js Server Component 可以读 cookie，但不能在渲染过程中可靠写 cookie；Route Handler 可以返回 `Set-Cookie`。这也让登录、初始化和错误映射集中在一个可验收边界内。
- **替代方案**：直接在 Client Component 使用 browser client 登录和写表。该方案可行，但会把初始化规则和数据库错误处理放进浏览器，并扩大客户端代码边界，因此不采用。

## 决策 2：会话刷新沿用根目录 Proxy，授权在数据源处再次执行

- **决定**：继续使用现有根目录 `proxy.ts` 调用 Supabase `auth.getClaims()` 刷新 SSR 会话；页面读取资料时仍通过服务端访问函数获取当前声明和用户数据，数据库则以 RLS 作为最终授权边界。
- **理由**：Next.js 16 的 Proxy 在路由渲染前执行，适合刷新 cookie；但官方指南明确不应只依赖 Proxy 做授权，数据读取和写入仍需靠近数据源验证。
- **替代方案**：仅在根布局判断会话。布局在客户端导航时不一定重新渲染，不能作为数据安全边界，因此不采用。

## 决策 3：匿名用户按 authenticated 角色设计 RLS

- **决定**：`profiles` 和 `user_preferences` 只向 `authenticated` 角色授予所需的读取、插入和更新权限；每条策略都限制 `user_id = auth.uid()`，更新同时设置 `USING` 与 `WITH CHECK`。
- **理由**：Supabase 匿名登录得到的用户仍使用数据库的 authenticated 角色，JWT 中另有匿名标记。按用户 ID 隔离即可同时服务本阶段匿名身份和后续邮箱绑定后的同一身份。
- **替代方案**：给 `anon` 角色开放表权限，或通过服务端高权限密钥写入。前者会放大未登录访问面，后者会绕过 RLS，均不采用。

## 决策 4：显式 GRANT 与 RLS 分开维护

- **决定**：迁移中先撤销 `anon` 的表访问，再明确授予 `authenticated` 最小权限，同时启用并定义 RLS。
- **理由**：数据库对象权限与行级策略是两层独立控制；Supabase 近期平台行为不再保证新表自动暴露给 Data API，显式授权可以避免环境差异。
- **替代方案**：只写 RLS、依赖项目默认授权。该方案可能在新项目或新平台默认值下导致合法请求全部失败，因此不采用。

## 决策 5：用户基础数据采用两个一对一表

- **决定**：`profiles` 保存展示与初始化状态，`user_preferences` 保存默认风格和场景偏好；两表均以 Auth 用户 ID 为主键并级联删除。
- **理由**：资料和偏好在后续阶段的变更节奏不同，分表保持边界清楚；主键同时作为外键天然保证每个身份最多一条记录，并让重试初始化保持幂等。
- **替代方案**：全部塞进一个 profile JSON 字段。短期文件更少，但后续设置和推荐需要独立读取偏好，语义不清，因此不采用。

## 决策 6：先创建私有桶和路径策略，不实现上传界面

- **决定**：创建私有 `wardrobe-images` bucket；对象名第一段必须等于当前用户 ID，并对读取、写入、更新和删除执行同样边界。
- **理由**：SDD-003 将直接使用该边界上传衣物原图；提前完成并验证安全底座，避免业务功能上线时再补权限。
- **替代方案**：等实现衣橱时才创建 bucket。这样会让 SDD-001 的“私有路径规则”无法独立验收，因此不采用。

## 决策 7：用户相关页面保持请求时渲染

- **决定**：服务端当前用户读取使用异步 cookie/声明，用户数据不做跨请求共享缓存；可复用的纯视觉壳保持静态。
- **理由**：cookie 是请求时 API，会使对应读取动态化；Supabase 匿名身份数据不能被 ISR 或公共缓存复用。
- **替代方案**：缓存完整首页或用户资料。存在跨用户内容混用风险，因此不采用。

## 决策 8：不新增依赖，采用现有质量门禁和可重复验证脚本

- **决定**：界面只复用已有 shadcn Button、Tailwind token 和 lucide 图标；隔离验证使用现有 Supabase JS；质量门禁仍为 `npm run check`，另执行生产构建和核心路径手工验证。
- **理由**：现有技术栈足以完成本阶段，新依赖不会带来必要价值。仓库脚本可以用真实匿名会话验证 RLS，而不需要引入测试框架。
- **替代方案**：引入状态库、ORM 或端到端测试框架。对一个应用底座阶段过重，因此不采用。
